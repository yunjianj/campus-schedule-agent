# v37：稳定删除确认与持久上下文

## 部署与升级

1. 首次部署先执行 `docs/schema.sql`；已部署 v35 的项目可以跳过基础建表。
2. **所有升级至 v36 的项目都必须执行 `docs/context-memory.sql`**。它新增两张记忆表、文档视图和 RPC，不改动已有日程、任务、复盘或用户画像。
3. 在 Supabase Database → Extensions 启用 `pg_cron`，执行 `docs/context-memory-cron.sql`。若扩展在迁移前已启用，迁移会自动注册同名任务。重复执行注册 SQL 更新同名任务，不创建多份任务。
4. 导入 `dist/校园日程智能体-v37.ifpkg`，保留 `BASE_URL`、`SUPABASE_KEY`、`USER_ID=demo`。核对新增“选择相关上下文”的模型后发布。
5. 使用新版本的新会话做下方验收。旧版本部署前的对话无法从仓库恢复，不补造原文或时间；现有用户画像与业务数据保留。

每日任务默认 19:00 UTC，即北京时间次日 03:00。Supabase Cron 使用 pg_cron 管理数据库定时任务，参见 [Supabase 官方说明](https://supabase.com/modules/cron)。**未启用 Cron 时仍会在每次输入的入口执行清理；没有输入的日子需要 Cron 才会定时清理。**

## v37 删除确认

v36 → v37 无需新 SQL 或环境变量。确认这一轮产生代码标志 `delete_confirmed`；为真时，路由和读取范围节点均只使用 `delete_candidates` 中经 UUID 校验的 ID，忽略模型给出的标题、日期与时间。读取实际记录后核对标题、日期、起止时间、地点和类别，完全一致才生成 DELETE 过滤器。

“确认删除”“好的，确认删除”“确认✅”可用于当前待删除操作；“保存”“就按这个排”不确认删除。没有当前确认状态或快照不完整时不执行。记录已经消失时直接说明，记录有变化时展示最新信息要求重新确认。查询和删除仍限定 `user_id`；重复记录按最初展示并确认的同组 ID 处理。

润色保留本轮数据库操作结论，不会在“已删除”正文旁边新增“没有待处理记录”。回归测试专门模拟确认时模型误带入错误标题、错误/无效日期和时间的情况，不能只用字段全空的理想模型响应验收。

## 每轮数据流

```text
本轮输入
  → begin_context_turn：补记上次失败日志、清理旧记忆、记录原文和开始时间
  → 读取当前聊天的工作状态、原始列表、近30天索引
  → 轻量模型选择相关条目或检索关键词
  → recall_context：验证来源、按对话时间/话题检索正文
  → 原有意图识别和业务链路：查库、录入、修改、确认删除、规划或复盘
  → AI 润色开场/收尾，同时提供语义摘要与话题
  → finish_context_turn：保存最终回复、摘要、操作事实及结束时间
  → 返回回复
```

重复的同一 `sys.workflow_run_id` 在同一聊天内只创建一条记录；已经完成的重复请求直接返回存档回复，不再次执行操作。不同聊天分别保存工作状态，同一聊天较早请求的迟到完成不会覆盖较新请求的状态。

模型选择索引只决定读取哪些材料，不直接决定删除、修改哪个数据库对象。所有写操作仍需按真实 ID 重新查库并校验。

## 文档内容与查看

`context_documents` 每个用户一份，保存文档版本、各聊天的工作状态和清理设置；`context_entries` 每轮一条，保存：

- 用户原文、最终回复，以及待完成 / 已完成 / 异常状态。
- 数据库生成的开始时间、结束时间、最近实际使用时间。存储为 `timestamptz`，聊天中按画像时区显示。
- 核心摘要、话题词，以及代码生成的意图、定位 ID、请求修改字段、真实回复摘录。
- 本轮新展示列表的不可变快照：来源聊天、展示时间、范围、完整编号、对象类型和数据库 ID。

`context_document_view` 可直接在 Supabase 查看完整原文和时间。聊天里可说：

```text
查看上下文文档
查看昨天的对话原文
删除昨天那张表的第一条
按刚才那张表，把第二条的位置改为主楼会议室
忽略之前的上下文
```

“忽略之前”清空当前聊天的引用和待执行状态，并建立自动检索边界；原始记录不会因此物理删除。明确要求查看旧历史时可以越过该边界。跨聊天可以检索历史，但不会自动继承另一个聊天的删除确认或待执行流程；首次使用历史编号必须明确来源。

文档原文不再只保留 6 轮。最近 6 轮纯文本摘要仍作为缓存，历史事实从持久化文档读取。图片由本轮视觉节点解析，不存图片二进制或重发历史图片；其抽取结果可体现在核心摘要与操作结果中。

## 稳定编号与当前焦点

当前状态分为三个部分：

- `active_list`：当前明确采用的完整编号列表，跨后续单条操作保持顺序。
- `last_referenced_items`：最近操作对象，用来理解“它 / 这条”。
- 待澄清候选：只在回答当前追问时使用，不覆盖原始查询列表。

查询两条后，修改第二条只更新该对象的当前信息，不覆盖原表；再删除第一条仍定位原来的第一条。删除后标记该编号已删除，不把原第二条移动成第一条。再次引用已删除编号会提示已经删除，不操作其他记录。

历史快照不变；当前列表的修改通过单独的更新映射保存。列表不再静默截成前20条；超过20条仍可按原编号选择。模型只接收列表的有界概览，完整编号由代码处理。列表 JSON 超过20000字符时要求缩小范围，不展示无法可靠保留编号的列表。新查询会激活新列表，单条操作回执不会激活新列表。

历史匹配多张表时，先显示“第1张 / 第2张”等来源。用户回复“第二张”后会恢复原请求中的修改要求或删除目标，无需重述。对话发生时间和活动日期独立处理：“昨天聊过的周三会议”不能被过滤成“昨天发生的会议”。

日程和任务栏分开展示。目前地点、时间、标题修改与删除链路操作日程表；待办任务不具有地点字段，不用日程编号去修改任务。

## 检索范围和输入上限

- 每轮入口返回最近30天最多100条索引；读取索引不刷新使用时间。
- 选择器可选最多8条索引记录，或给出最多10个话题关键词。关键词可检索仍未过期的更早历史；明确日期以用户时区转换成对话时间区间。
- 注入意图模型的历史正文合计约12000字符，以摘要和有界原文片段组成。原始全文仍在数据库，未被截断覆盖。
- 聊天查看原文最多展示约40000字符，超长时明确提示只展示部分，数据库视图中可查看完整记录。
- 用户画像保留学期、节次、时区、允许/禁用时段、学习禁用时段、每日块数和回复风格。密钥和服务身份不进入模型材料。

## 自动删除策略

默认 **超过90天没有被实际召回使用**的记录会物理删除，包括该条原文、摘要、回复和列表快照；删除后不支持从记忆系统恢复。不会删除 `schedules`、`tasks`、`reviews` 或 `user_context`。

实际召回内容会更新 `last_accessed_at`；仅刷新索引不会使全部旧记忆续期。每次清理最多5000条，大量积压由后续请求/定时任务继续处理。关联的过期列表指针和焦点也会清理，不允许旧缓存恢复成可执行编号。

近期未完成操作引用的来源列表暂时受保护；**聊天7天无活动后，旧草稿、待确认操作和候选过期**，不再为来源列表提供保护。默认90天保留与7天临时状态保护分别控制原文留存和执行状态，避免未完成流程无限保留旧记忆。

配置在 `context_documents`，可在 Supabase 表编辑器修改，也可执行：

```sql
-- 将未使用记忆保留期改为180天；范围1–3650天。
update public.context_documents set retention_days=180 where user_id='demo';

-- 临时关闭物理删除；仍会使长期不活动的待执行状态过期。
update public.context_documents set auto_delete_enabled=false where user_id='demo';

-- 恢复自动删除。
update public.context_documents set auto_delete_enabled=true where user_id='demo';

-- 检查每日任务及最近执行结果。
select jobid,jobname,schedule,active from cron.job where jobname='campus-context-cleanup';
select * from cron.job_run_details
where jobid in (select jobid from cron.job where jobname='campus-context-cleanup')
order by start_time desc limit 10;
```

首次请求创建文档后才能修改该行；如果希望在首次使用前设置，可先 `insert into public.context_documents(user_id) values('demo') on conflict do nothing`。

## 失败、重试与已知限制

- 文档入口读取失败时停止本轮操作，不退回全表搜索。新 SQL 未部署时回复明确提示检查 v36 迁移。
- 文档尾部保存失败时保留业务结果，明确提示记忆未同步；下一轮仅补记旧日志，不重复操作日程。已按保留期清理的旧日志不再重新补造。
- 业务数据库失败不记为成功。工作流中断后可能留下待完成条目；7天后清理将其标记异常，不编造未发送的回复。
- 文档保存和日程操作不是同一个跨服务事务。日志去重依赖 Dify 的本轮运行 ID；新的运行 ID 会被当成新的输入，网络异常后应先核对日程。
- 当前仍为 `demo` 单用户演示，未新增登录或多人权限；需在目标环境验证实际模型输出、SQL权限与 Cron 状态。
